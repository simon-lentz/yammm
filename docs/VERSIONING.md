# yammm Versioning Policy

This document codifies yammm's versioning commitments — both API and wire-format — so consumers and contributors have one authoritative reference for what a given release bump is permitted to change. Added in v0.3.0 release prep.

## Scope

yammm's versioning covers two surfaces that evolve on related but distinct cadences:

1. **Go API surface** — exported types, functions, methods, constants, options, and their documented behavior under the `github.com/simon-lentz/yammm` module.
2. **`.ys` wire format** — the on-disk shape of snapshots produced by `snapshot.Marshal` and consumed by `snapshot.Load` / `snapshot.Info` / `snapshot.HeaderOnly` / `snapshot.Verify`. The wire format carries its own `version` field in the header (currently `2` as of v0.3.0).
3. **Generated Go output (`adapter/gogen`)** — the shape of the Go source `gogen.Marshal` emits for a given schema and options. Promoted to a committed surface in v0.6.0 (the v0.5.0 notes anticipated promotion "if a downstream consumer comes to depend on that shape"; a downstream consumer now byte-pins committed generated packages against it). Its tier rules are in "Generated-output surface" below.

The surfaces share a semver tag but have independent version-bump triggers, documented below.

## Pre-1.0 policy (current)

yammm is currently pre-1.0. Under Go module semver conventions, `0.X.Y` releases are understood to be unstable — backward-incompatible changes are permitted at minor-version bumps — but yammm's own policy is narrower than that. The following rules apply:

### Minor releases (`v0.X.0 → v0.X+1.0`) may include:

- **Additive API changes** — new exported symbols, new option types, new methods on existing types, new struct fields added at the end of a struct (subject to the type's own versioning contract, if any). Consumers written against the prior release continue to compile and run unchanged.
- **Subtractive and breaking API changes** — removal of exported symbols, and breaking changes to an exported symbol's signature, name, or type (e.g. changing a method's return type, renaming an exported function, or collapsing two carrier types into one), provided (a) a grep across the known consumer set returns **either** zero external Go references **or** external references confined to a consumer that pins an older yammm release and whose migration is tracked as a downstream backlog item — in which case the semver pin carries the coordination, so tagging the breaking release cannot break that consumer's build and the migration lands on the consumer's own schedule; (b) the change is explicitly documented in the release notes; and (c) the release-notes entry enumerates every removed, renamed, or signature-changed symbol for downstream auditing.
- **Behavior tightenings** — changes where the only observable difference is that a previously-erroring call becomes a no-op for input that was already semantically equivalent to the stored state, or similar correctness-preserving narrowings (e.g., `Registry.Register` becoming idempotent for exact-`SourceID` + exact-`StructuralHash` re-registration in v0.3.0). Documented in the release notes with the specific contract change.
- **Wire-format additions** — new optional fields added under the `omitempty` + header `features`-signal convention, provided the new field's absence in an older reader does not cause silent data loss. A v0.X reader consuming a v0.X+1-produced document skips the unknown field; a v0.X+1 reader consuming a v0.X-produced document reads missing fields as their zero value.

### Wire-format-incompatible changes require a format-version bump:

Any wire-format change whose absence in an older reader would cause **silent data loss** is required to:

1. **Increment the header's `version` field** (e.g., `1` → `2`).
2. **Rely on yammm's existing unknown-version-rejection semantics** — older readers encounter the new version and return Fatal `E_SNAPSHOT_UNSUPPORTED_VERSION` rather than partial-parsing a document they do not fully understand.
3. **Document the bump and the asymmetric-reader semantics** in the release notes: which older versions accept the new file (if any — typically none), which newer versions accept the older file (typically the immediately-prior N versions, losslessly).

The canonical example is v0.3.0's `UnresolvedEdge.Properties` addition: the new wire field cannot be `omitempty`-safe alone because a pre-v0.3.0 reader would silently drop edge properties on cross-batch unresolved edges. The v1 → v2 bump forces pre-v0.3.0 readers to reject cleanly; v0.3.0+ readers accept both v1 and v2 files (v1 files have no Properties to drop, so the read is lossless).

Wire-format version bumps are permitted at minor-version bumps during pre-1.0 (they are the yammm-native signal for "this format has diverged"); they are not deferred to major bumps under pre-1.0.

### Patch releases (`v0.X.Y → v0.X.Y+1`) are reserved for:

- Bug fixes that preserve the public API and wire format.
- Documentation-only changes.
- Internal refactors, test improvements, and dependency updates.
- **Additive API changes** — new exported symbols whose addition leaves every existing signature and documented behavior unchanged; consumers written against the prior release continue to compile and run unchanged.

Patch releases never introduce breaking changes: no removed or renamed exported symbols, no signature changes, no tightenings of documented behavior, and no wire-format changes. Anything in those categories requires at least a minor release.

## Generated-output surface (`adapter/gogen`)

For an unchanged schema, unchanged `Marshal` options, and an unchanged yammm version, generated output is byte-identical (all walks and name assignments are deterministic). Across versions, changes to the output classify as:

### Breaking (major post-1.0; pre-1.0 minor under the standard subtractive rules):

- Renaming or removing any emitted identifier derived from an unchanged schema: struct names, field names, named DataType/enum types and their value constants, `EDGE_` struct names, `Graph` fields, or the `SerializedModel` / `SerializedModelEntry` / `SchemaHash` declarations.
- Changing the type-mapping table (e.g. `Integer` → anything other than `int64`), the pointer-optionality rules, the json-tag shape, or the `Where`-block contract of `EDGE_` structs.
- Changing the `SerializedModel` re-load semantics (the documented `LoadString` / `LoadSourcesWithEntry`-with-`"."` recipes) or the meaning of `SchemaHash` (`schema.StructuralHash`).

### Additive / behavioral (minor or patch, release-noted):

- New emitted declarations in support of new schema features.
- Identifier derivation for new inputs (e.g. additions to the default initialisms set) — existing identifiers for existing inputs must not change.
- Byte-level changes that rename no identifier and change no semantics (comment text inside the generated file, formatting). Consumers that byte-pin via drift gates will see these and regenerate; the release notes must call them out.

### Explicitly uncommitted:

- Doc-comment prose inside generated files.
- Declaration order beyond "deterministic for a given yammm version".

The golden corpus under `adapter/gogen/testdata/` is this contract's executable form: a golden may change only in a release whose notes account for the change under the tiers above.

## Post-1.0 policy (future)

After the `v1.0.0` release, yammm commits to the stricter semver contract that consumers expect from a stable library:

### Major releases (`vN.X.Y → vN+1.0.0`) are required for any change that:

- Removes an exported symbol.
- Changes an exported symbol's signature (parameter types, return types, method set).
- Tightens an exported contract in any way that changes observable behavior (errors become silent, nil returns become non-nil, success paths change their side-effect shape).
- Bumps the `.ys` wire format version.
- Introduces a new required field, new required option, or any other change that forces consumers to update call sites.

### Minor releases (`vN.X.Y → vN.X+1.0`) are for strictly additive changes:

- New exported symbols (types, functions, methods, constants).
- New options that default to pre-existing behavior when omitted.
- New wire-format fields with `omitempty` semantics that do not trigger silent data loss on older readers.
- Documentation, test, and internal-refactor improvements that preserve the public API surface.

### Patch releases follow pre-1.0 patch-release rules verbatim.

## v0.5.0 under this policy

v0.5.0 bundles additive feature work (Go source generation, internal dispatch hardening) with one **breaking contract tightening** (schema-level primary-key enforcement). The Go API symbol surface and the `.ys` wire format are unchanged — code written against `v0.4.x` compiles and runs unchanged — but the **schema-loading contract is tightened**: a schema that loaded cleanly under `v0.4.x` can now be rejected (see the primary-key-enforcement bullet).

- **Additive API surface (`adapter/gogen`)** — a new leaf adapter package exporting `Marshal(s *schema.Schema, opts ...Option) ([]byte, error)`, the `Option` type, and the `WithPackageName` / `WithInitialisms` options. It generates Go source from a schema (one struct per type, named Enum/DataType types, owner-qualified `EDGE_` association structs, a `Graph` aggregate, and an embedded `SerializedModel`) and is schema-in, bytes-out — it imports the Primary API and is never imported back, consistent with the documented adapter-layer discipline. Strictly additive. Justified under the pre-1.0 "additive API changes" rule.
- **Additive CLI surface** — a new `yammm gen --to go <schema.yammm>` command (`cmd/yammm`), sibling to `export`, with `--package`, `--output`, and `--initialisms` flags. The CLI binary is outside the two formally-versioned surfaces (Go API + `.ys` wire format); the addition is backward-compatible (no existing command changes), noted here for completeness.
- **Internal hardening (no API impact)** — the `//exhaustive:enforce` rollout to the seven remaining `schema.ConstraintKind` dispatch switches (so a newly-added kind fails CI rather than reaching a backend un-handled), and the new `internal/ident.ToUpperCamelInitialisms` mechanism that `adapter/gogen` reuses. Both are internal — `internal/*` carries no compatibility guarantee — and change no exported behavior.
- **Breaking schema-loading tightening (primary-key enforcement + extends resolution)** — schema completion now rejects three schema shapes that loaded cleanly under `v0.4.x` via `schema.Load` / `LoadString` / `LoadSources`: (1) every **concrete** (non-abstract, non-part) type must declare or inherit at least one `primary` field, else `E_NO_PRIMARY_KEY`; and (2) an **association** (`-->`) must target a **concrete** type — an abstract target is now rejected with `E_INVALID_ASSOCIATION_TARGET` (a part target already was); and (3) a **concrete** type whose `extends` clause names a **qualified** supertype that does not resolve — an undefined import alias, or a type absent from the imported schema — is now rejected with `E_UNKNOWN_TYPE` when the load supplies a registry (every source-backed load does); previously such a reference was silently deferred, dropping all inheritance from that supertype with no diagnostic (an unqualified unknown supertype already errored). For (1) and (2), a node needs identity to enter a graph or be addressed by an edge, so both checks are hoisted from graph-construction / generation time to load time; (3) brings qualified `extends` resolution in line with the existing unqualified-supertype and relation-target handling. This tightens an exported contract (the schema-loading success path now errors for inputs it previously accepted) — normally **major-requiring**, but permitted in this pre-1.0 minor under the **amended rule (a)**: the affected inputs are `.yammm` schemas, and the only external consumer was pinned to an older release and migrates on its own schedule, so tagging `v0.5.0` cannot break its build. Per conditions (b)/(c), the release notes enumerate the three newly-rejected schema shapes and their diagnostic codes. (Composite primary keys — multiple `primary` fields — are **not** new; they were always supported, and v0.5.0 only corrects documentation that wrongly said "exactly one", which is not a breaking change.)

The `.ys` wire format is unchanged at v0.5.0 (header `version` stays `2`); `adapter/gogen` neither reads nor writes `.ys` (its embedded `SerializedModel` is verbatim `.yammm` source, re-loadable via `schema.LoadString` / `LoadSourcesWithEntry`). The shape of gogen's generated Go output (struct layout, `EDGE_` / `Graph` naming, `SerializedModel` form) is pinned by the package's golden corpus but is **not** yet a formally versioned surface under this policy; if a downstream consumer comes to depend on that shape, a future revision can promote it to a committed surface. The additive surface is documented inline in the v0.5.0 release notes with pointers back to this document's relevant policy sections.

## v0.6.0 under this policy

v0.6.0 closes two gogen feature requests and folds in the test-infrastructure review that followed. The release carries bug fixes and additive API plus one **breaking test-helper surface reduction** — the removal set below is what lifts the release from the patch tier (where this work was first drafted as v0.5.2) to a minor:

- **Bug fix (restores documented behavior) — module-root-relative `SerializedModel` keys.** `adapter/gogen`'s package documentation has always promised module-root-relative embedded keys and a re-load that "needs no filesystem"; the implementation relativized against the entry schema's directory and silently fell back to cwd-relative disk reads when the load's module root differed (registry-style layouts: `schema.Load` + `WithModuleRoot(repoRoot)`). Keys now derive from the load's recorded module root (`Schema.ModuleRoot()`), so they match the import statements inside the sources and the embedded model re-loads hermetically from any working directory. `Marshal`'s round-trip self-check now runs with `WithSourcesOnly`, so a key regression fails generation loudly instead of being rescued by on-disk files. Generated bytes change only for module-root ≠ entry-dir loads (the shapes that were previously self-contradictory) plus one added comment line in the multi-source re-load instructions; the pre-existing golden corpus is otherwise byte-identical.
- **Bug fix — in-memory source keys resolve textually.** `LoadSources` / `LoadSourcesWithEntry` pre-registration resolved each joined key path against the filesystem (symlinks included) whenever it happened to exist on disk, while import lookup never did — so a root-relative key reachable through a symlinked directory registered under a different `SourceID` than the one import resolution computed. Under `WithSourcesOnly` that mismatch failed the load (and therefore `gogen.Marshal`'s round-trip self-check) for schemas that load fine from disk, dependent on the process working directory's contents. Root-relative keys now derive textually from the canonical module root on every path — pre-registration, entry selection, import lookup, and the sandboxed disk reads — making in-memory resolution independent of disk state. Absolute keys (the LSP overlay shape) still canonicalize like entry paths so they land in the same path regime as the module root.
- **Bug fix — cross-Load registry cache hits now carry their sources.** A shared-`WithRegistry` load whose import short-circuited to a registry-cached schema produced a `Schema` whose `Sources()` lacked the cached import's content — breaking closure-content consumers (gogen's embedded model; cross-import diagnostics rendering). The cache-hit path now copies the cached schema's transitive closure content into the new load's source registry. The copy memoizes per load — a diamond-shaped import graph is walked per schema, not per import path — and a copy that collides with different pre-registered bytes under the same `SourceID` surfaces as `E_INTERNAL` instead of silently leaving `Sources()` divergent from the compiled import.
- **Bug fix (restores documented behavior) — float exponents without a sign.** The lexer's exponent fragment required an explicit sign, rejecting the signless form the published numeric-literal grammar documents — the grammar's own example `2.5e10` failed to load with `E_SYNTAX`. The sign is now optional, so previously-rejected spec-conformant schemas load; signed forms are unchanged.
- **Diagnostics — malformed numeric literals are named at the literal.** A numeric literal running straight into identifier characters (`0x10`, `42abc`, a broken exponent) now lexes as one malformed token, and the load reports `malformed numeric literal "0x10": numeric literals are decimal (hexadecimal and suffixed forms are not supported)` spanning the literal itself — previously the error was a `mismatched input` pointing at whatever happened to follow. The code stays `E_SYNTAX`; no new diagnostic codes. One pathological acceptance change rides along, enumerated for completeness: the word operator `in` written flush against a preceding number (`1in [1, 2]`) previously token-split and parsed; it is now a malformed literal and requires whitespace, like every other operand boundary already did in practice.
- **Breaking — `snapshot/snapshottest` surface reduction.** The package's exported surface was rebuilt around structural round-trip assertions. Removed: `BuildTestSnapshot`, `Record`, `CompareSnapshots`, `ReadGolden`, `UpdateGolden`, `State`, `ExpectDirState`, `ExpectMetadataPreserved`. Signature change: `AssertDeterministic` drops its unused `*schema.Schema` parameter. Replacements: `DiffSnapshots` (go-cmp structural comparison — recursive over composition trees, provenance-presence-aware, exact for same-typed numerics) supersedes `CompareSnapshots`; `BuildSnapshot` supersedes the `BuildTestSnapshot`/`Record` pair for pre-validated instances; golden read/write/update moved to internal test support. Justified under the amended pre-1.0 rule (a): the only external consumer was pinned to an older release and migrates on its own schedule. Per conditions (b)/(c), this enumeration is the removed-symbol audit record.
- **Breaking — `schema.WithSourceRegistry` unexported.** The load option's parameter type lives in `internal/source`, which external consumers cannot import or name — the only argument expressible outside the module was an untyped nil — so the symbol was public in name only. It is now unexported. Its sole consumer, the in-module LSP analyzer, instead copies the loaded schema's source closure from the public `Schema.Sources()` accessor after the load. Rule (a) is satisfied trivially: no meaningful external reference was ever constructible. Enumerated here per conditions (b)/(c).
- **Breaking — `schema.Builder` name validation.** `Build()` now rejects (`E_INVALID_NAME`) declared names that do not match the DSL's own name productions: type and datatype names must match `UC_WORD` (`[A-Z][A-Za-z0-9_]*`), property names `LC_WORD` (`[a-z][A-Za-z0-9_]*`), and relation names either form (`[A-Za-z][A-Za-z0-9_]*`). Previously the Builder checked names only for emptiness — its own `validateInput` documentation already promised rejection of "empty/invalid identifiers" — so it admitted schemas the DSL cannot express (e.g. `AddType("Foo-Bar")`), which could not round-trip to `.yammm`, mangled through gogen identifier generation, and surfaced only as label collisions at neo4j export. Schema names and invariant names map to quoted strings in the DSL and stay free-form; import aliases were already validated during completion (`E_INVALID_ALIAS`). A correctness consequence: `adapter/neo4j.SanitizeIdentifier` is the identity function on every production-conformant name, so two distinct type names from either schema front door can no longer collide after sanitization — `DetectLabelCollisions` is retained as defense-in-depth. This tightens an exported contract — permitted in this pre-1.0 minor under the amended rule (a): the only external consumer was pinned to an older release and migrates on its own schedule. The affected front door is the programmatic `Builder`; `.yammm` source loading via `Load` is unchanged. Per conditions (b)/(c), the newly-rejected input classes are the three production mismatches enumerated here.
- **Additive API surface (`schema`)** — `Schema.ModuleRoot()` (the canonicalized module root the load resolved module-style imports against; `""` when none was in play) and the `WithSourcesOnly()` load option (import resolution restricted to pre-registered in-memory sources; a miss is `E_IMPORT_RESOLVE`, never a filesystem read).
- **Additive API surface (`diag`)** — `Result.HasCode(code Code) bool`, the code-presence predicate alongside the existing severity predicates.
- **Additive API surface (`instance/instancetest`)** — a new test-support package exporting the `VI` instance builder (`VI(typeName string, opts ...VIOption) *instance.ValidInstance`) and its options (`TypeID`, `PK`, `Props`, `Edges`, `Composed`, `Provenance`), the shared constructor for pre-validated instances across the graph, snapshot, and adapter test suites.
- **Additive API surface (`snapshot/snapshottest`)** — `BuildSnapshot` and `DiffSnapshots`; see the breaking bullet for what they replace.
- **Additive API surface (`lsp`)** — `Config.DebounceDelay time.Duration`, the delay between a document change and the analysis it triggers (zero or negative means the 150ms default). Promotes a workspace-internal test-only setter into real configuration; existing `Config` literals compile and behave unchanged.
- **Additive CLI surface** — `yammm gen --module-root <dir>` resolves module-style imports against a root other than the schema's own directory; without it, registry-layout schemas could not be generated by the CLI at all. CLI diagnostics across all schema-loading subcommands now relativize locations against the loaded schema's module root (canonical, symlink-resolved), so rendered paths stay root-relative regardless of symlinks in the invocation path. `yammm-lsp` gains a `--debounce-delay <duration>` flag exposing the new `lsp.Config.DebounceDelay` (0 keeps the 150ms default).
- **Surface promotion** — generated Go output is now the third formally versioned surface (Scope item 3 + the "Generated-output surface" tier rules above). A documentation/policy commitment; precedent for landing a policy edit alongside a release is v0.5.1's amendment of the patch rule itself.

The `.ys` wire format is unchanged at v0.6.0 (header `version` stays `2`).

## v0.7.0 under this policy

v0.7.0 bundles the diagnostic-completeness rework (behavioral — one load pass reports every independent error exactly once) with one **breaking schema-loading tightening** (unknown property datatypes). The Go API symbol surface gains three additive `diag` symbols; the `.ys` wire format is unchanged.

- **Behavioral — diagnostic completeness.** Schema loading no longer fail-fasts at the first import-declaration error, the first failed import, or the first failing completion phase. On inputs that already failed, strictly more — and more truthful — diagnostics are reported, under the same codes and the same all-or-nothing contract (any error ⇒ nil `*Schema`). The coordinated changes, enumerated:
  - *Import continuation* — every unresolvable or failed import is reported at its own declaration; semantic analysis then proceeds with the failed aliases deferred, so the schema's own diagnostics surface in the same pass.
  - *Structural-rejection continuation* — `LoadString` and `WithDisallowImports` loads still reject import declarations categorically (single `E_IMPORT_NOT_ALLOWED`, never probed), but the rejection no longer suppresses the source's other findings.
  - *Failure memoization* — within one load, a schema that fails to compile is compiled once; each importer still reports its own `E_UPSTREAM_FAIL` at its own declaration (previously a diamond over a broken import would have re-collected the broken schema's diagnostics per importer once continuation landed).
  - *Per-schema error attribution* — a load shared across nested schemas judges each schema by the errors it contributed, so a clean import loaded after a broken sibling compiles and registers instead of drawing a false `E_UPSTREAM_FAIL`.
  - *Keep-first alias binding* — an import alias binds once; a later declaration of a bound alias is reported once (`E_DUPLICATE_IMPORT`, by completion) and stays inert: not loaded, not resolved, not wired. This also fixes a latent mis-wire where the kept import could silently resolve against the last declaration's schema.
  - *Validation ownership* — declaration-level import validation lives in completion (shared by parse and Builder front doors; its alias-collision check now also covers local datatype names — newly rejecting one previously-clean Builder input, carved out in the strictness note below), resolution-level validation in the resolvers; no check is live in two layers, so continuation cannot double-report. The duplicate-resolved-`SourceID` check now visits declarations in source order, deterministically blaming the later declaration (previously map-iteration-dependent).
  - *Cascade suppression* — references through a failed **or completion-rejected** import alias (`extends`, relation targets, property datatypes, primary-key types) defer silently to the root-cause diagnostic; a declared-but-rejected `primary` draws `E_INVALID_PRIMARY_KEY_TYPE` **once at the declaring type** (not re-reported at every inheriting subtype, and never an additional `E_NO_PRIMARY_KEY`); invariant validation skips types with unresolved supertype chains.
  - *Completion gates removed* — all completion phases collect-and-continue; only inheritance-cycle detection keeps a hard gate (linearization requires cycle-free input). Duplicate type/datatype declarations are now all reported (keep-first), not just the first.
  - *Truncation surfacing* — `diag.Collector` counts every issue it *sees* (not only those stored under the limit), so `HasErrors`/`OK`/`ErrorCount`/`SeverityCounts` stay truthful when collection is truncated and the all-or-nothing gate cannot be fooled by a dropped error; the CLI appends a dropped-issues note in text mode and emits the truncation wire fields (`limit`/`limitReached`/`droppedCount`) in JSON mode — now including a truncated result with no rendered errors, previously silent; the LSP logs truncation server-side.

  Two `Builder`-front-door exceptions aside, no input that loaded cleanly under `v0.6.0` is rejected by this stream, and no input that failed under `v0.6.0` loads — verified by strictness controls in the test suite. **Exception 1 (a breaking tightening):** a `schema.Builder` import whose alias equals a *local datatype* name now fails with `E_IMPORT_ALIAS_COLLISION` (the completer's collision check previously consulted only the type index, and the loader's datatype-aware check never ran for `Builder` schemas; the `Load*` front door already rejected this shape at `v0.6.0`, so only the programmatic `Builder` API tightens) — justified under the same **amended rule (a)** as the unknown-property-datatype entry below (the only external consumer was pinned to an older release). **Exception 2 (a loosening):** a registry-less `Builder` (no `WithRegistry`) whose primary key is typed by a qualified datatype (`id other.IdType primary`) previously failed load with a mis-attributed `E_INVALID_PRIMARY_KEY_TYPE`; it now defers that reference to link time and loads clean, consistent with how a registry-less `Builder` already defers a qualified `extends`, relation target, and non-primary property datatype (pinned by `TestBuild_NoRegistryQualifiedPrimaryKey_DefersAtLinkTime`) — a permissive behavioral change (a previously-rejected shape now accepted) needing no special justification. Both exceptions are `Builder`-API-only and production-unreachable (the `Load*` front door always supplies a registry, so only the programmatic `Builder` reaches these cases); schema-author-facing `.yammm` input is unaffected by either. Otherwise the stream is justified under the pre-1.0 "behavior tightenings" rule (more complete reporting on already-failing inputs); minor tier, never a patch.
- **Additive API surface (`diag`)** — `Collector.ErrorCount() int`, the Fatal+Error count alongside the existing predicates (enables before/after comparison when one collector is shared across nested operations); `Result.TruncationNote() string`, the canonical one-line dropped-issues summary ("" when the limit was not reached) so text-rendering consumers share one wording; and `IsImportDeclarationCode(code string) bool`, which classifies a rendered diagnostic-code string as an import-*declaration* diagnostic (rejected / duplicate / colliding / invalid alias) versus an import-*resolution* one, co-located with the code definitions so the LSP markdown surface's Hint-downgrade list cannot drift from the codes (a `CategoryImport` partition-guard test pins every import code to exactly one family).
- **Breaking — unknown property datatype tightening.** Property datatype references that loaded silently under `v0.6.0` are now rejected at load with `E_UNKNOWN_TYPE`: (1) an **undeclared local name** (`a Mystery` with no `type Mystery = …`); (2) a **qualified reference whose import resolves but lacks the datatype** (`a other.NoSuchType`) — including a property typed by an imported *type* rather than a datatype, which the DSL grammar does not back (a property's type must be a built-in or a datatype alias; type references belong in relations); and (3) a **qualified reference whose qualifier names no declared import** (`a nope.SomeType`). Previously all three loaded cleanly and the failure surfaced per-value at instance-validation time ("unresolved alias constraint") — or never, for an optional property absent from the data. References through a declared-but-failed import remain silent (the import failure is the root cause), and Builder/deferred completion flows without a registry or resolution map keep their deferred posture. One attribution correction rides along: an unknown-named `primary` property previously failed load with a mis-attributed `E_INVALID_PRIMARY_KEY_TYPE` ("Alias cannot be used as a primary key"); it now fails with the root-cause `E_UNKNOWN_TYPE` — no input flips between accept and reject, only the code changes. This is the same class as v0.5.0's loading tightenings — normally major-requiring, permitted in this pre-1.0 minor under the **amended rule (a)**: the only external consumer was pinned to an older release and migrates on its own schedule. Per conditions (b)/(c), this enumeration is the newly-rejected-shapes audit record.

The `.ys` wire format is unchanged at v0.7.0 (header `version` stays `2`).

## v0.9.0 under this policy

v0.9.0 carries two independent streams. The headline is **schema annotations**: a validated `@name` / `@@name` decorator mechanism on the DSL, whose first consumers are Neo4j index DDL and a write-once node-write shape. The second closes the two instance-layer edge-validation root causes surfaced by the jschema contract-alignment suite — schema completion never resolved datatype-alias constraints on association edge properties, and the instance layer re-resolved relations' declaring-schema-relative target names against the entry schema.

Minor-tier. The annotation stream is additive across the DSL, the Go API, and the CLI, with behavior changes on existing surfaces (two CLI commands, the Neo4j node-write shape for annotated types, and — confined to failing loads — the `E_PROPERTY_CONFLICT` reporting shape); the edge-validation stream carries a breaking schema-loading tightening, a data-validation tightening, and two additive API symbols.

### Schema annotations

- **Additive DSL surface — annotations.** A property may carry trailing `@name` / `@name(args)` decorators, and a type body may carry `@@name(args)` members (optionally doc-commented). The blessed v1 set is `@index` (single-property range index), `@@index(p1, p2, …)` (composite, order significant), `@vector(cosine|euclidean)`, and `@writeOnce`; the set is curated in the core, with no external registration API. Annotations are validated at load after inheritance linearization, and inherited through it — a subtype's set is the **union across its direct supertypes' own resolved views**, so a marker like `@writeOnce` cannot be dropped by `extends` order, and a type's deliberate shadowing binds its own subtypes rather than being undone by a grandparent's copy. Never declaring an annotation and deliberately dropping one are distinguished: when one supertype carries an annotation that another dropped, the two disagree and the load reports `E_INVALID_ANNOTATION` rather than silently picking a side; re-declaring the property on the subtype, with or without the annotation, settles it. **Purely grammar-additive:** `@` previously lexed as a token that appeared in no rule, so every annotation-bearing schema was a syntax error. No previously-valid schema parses differently or changes meaning. See [SPEC.md](SPEC.md#annotations) for the full surface and its diagnostics.
- **Additive API surface (`schema`) — the annotation model.** `Annotation` (`Name`, `Args`, `Documentation`, `Span`); `AnnotationArg` (`Text`, `Kind`, `Span`); `AnnotationArgKind` with `ArgUnvalidated` / `ArgPropertyRef` / `ArgKeyword`; `AnnotationPlacement` with `PlacementProperty` / `PlacementType`; `AnnotationSpec` (`Name`, `Placement`, `Documentation`, `ArgHint`) with `AnnotationSpecs()` — a read-only view of the built-in registry for editor tooling, not a registration API — and `VectorSimilarityFunctions()`, so tooling cannot offer a keyword the loader rejects. Accessors: `Property.Annotations()` / `AnnotationsSlice()` / `Annotation(name)`, and `Type.Annotations()` / `AnnotationsSlice()` / `AllAnnotations()` / `AllAnnotationsSlice()` (own, and own-plus-inherited). Builder entry points: `TypeBuilder.WithTypeAnnotation(name, args...)` and `TypeBuilder.WithPropertyAnnotation(propertyName, name, args...)`, both routed through the same completion-phase validation as the parse front door. Justified under the pre-1.0 "additive API changes" rule.
- **Additive API surface (`schema`) — merged-view property identity.** `Property.Origin() *Property` returns the property **as declared** — itself when nothing was merged. It exists because annotation union can make an entry in `Type.AllProperties()` / `AllPropertiesSlice()` a *synthesized copy* rather than the `*Property` its declaring type holds in `PropertiesSlice()`, which silently broke the pointer-keyed lookups three generator adapters relied on. Any map built from declared properties and read back over a merged view must key through `Origin()`; everything it discards is annotation state (name, constraint, datatype reference, optionality, primary-key status, span, and declaring scope are all preserved on the copy). Additive symbol, but a **contract that identity-keyed consumers must adopt** — documented in [API.md](API.md#annotations).
- **Additive diagnostic codes (`diag`)** — `E_UNKNOWN_ANNOTATION`, `E_UNKNOWN_ANNOTATION_TARGET`, `E_INVALID_ANNOTATION`, `E_INVALID_ANNOTATION_TARGET`, and the Warning-severity `W_ANNOTATION_SHADOWED` (a type's own re-declaration shadows an inherited annotated property without re-stating the annotations, silently dropping them). `adapter/neo4j` adds `E_NEO4J_UNKNOWN_PROPERTY` (an index annotation naming a property the type does not have) and `E_NEO4J_INVALID_INDEX_TARGET` (one naming a property whose type cannot carry it — `@index` on a non-scalar, `@vector` on a non-Vector or on a non-positive dimension). Both are reachable only where load-time validation had to defer, on a type whose supertype never resolved and on every qualified reference in a registry-less `schema.Builder` schema. No existing code changes meaning; no schema that loaded clean at v0.8.0 gains a diagnostic, since annotations could not parse.
- **Additive API surface (`adapter/neo4j`) — index emission and diffing.** `IndexKind` (`IndexRange`, `IndexVector`) and `Index` (name, kind, label, properties, vector dimension/similarity, complete `CREATE … IF NOT EXISTS` statement); `Adapter.IndexesForSchema` (statements) and `Adapter.IndexesStructured` (values); `Adapter.DiffIndexes` with `IndexDiffResult` (`Match` / `Drift` / `Create` / `Drop` / `Unverified`), `IndexMatch`, `IndexDrift`, and `IndexUnverified`; `IndexKind.String()` so an `Index` renders as `RANGE`/`VECTOR` rather than a bare ordinal. `RemoteIndex` gains `Options map[string]any`, `State`, and `OwningConstraint` fields **at the end of the struct**, plus `VectorDimensions()`, `VectorSimilarity()`, and `IsOnline()` accessors. `ConstraintDiffResult` gains an end-of-struct `Unverified []ConstraintUnverified` field with the `ConstraintUnverified` type. `NodeShape` gains an end-of-struct `ImmutableKeys []string`. `ImmutableKeysFor(t *schema.Type) []string` exposes a type's derived `@writeOnce` keys. Justified under the pre-1.0 "additive API changes" rule (the `RemoteIndex` field under its end-of-struct clause).
- **Behavior change — `IntrospectIndexesQuery()` returns a widened query over a wider row set.** Two changes, and a direct caller of the returned string is exposed to both. The projection now also yields `options` (vector-index configuration) and `state` (so an index that exists but serves no queries is distinguishable from a healthy one); executing it against a server that does not support those columns fails where it previously succeeded, so the widening is effectively a server-version requirement. Separately, the `WHERE owningConstraint IS NULL` clause is **gone**: the query now returns constraint-backing indexes alongside standalone ones, filtering only `LOOKUP`. Those rows are what let the diff see that a backing index holds its constraint's name against every `CREATE INDEX` and already serves the definition it covers — both conditions under which the server silently no-ops a declared index. A consumer that filtered on the query's behalf must now test `RemoteIndex.OwningConstraint` itself rather than assume the rows were excluded. `yammm neo4j diff` handles an unsupported server by degrading (see below); a direct caller does not.
- **Behavior change — `@writeOnce` changes the emitted Neo4j node-write shape.** The effective immutable-key set for a written type is now `WithImmutableKeys` ∪ the type's derived `@writeOnce` keys. A node whose effective set is non-empty is written with the split `ON CREATE SET` / `ON MATCH SET` shape, and `$update_props` excludes every member of that set; `BatchNodeQueries` selects the shape **per type**, so an annotated type gets the split shape while an unannotated type in the same snapshot stays mutable. A non-empty explicit list still produces the split shape for every written type, preserving the prior contract, and only the explicitly-passed keys are validated against the schema (the derived ones come from validated annotations by construction). A schema with no `@writeOnce` emits byte-identical single-node Cypher to v0.8.0. The guarantee does not depend on the caller holding a `*schema.Type`: the derived keys travel on `NodeShape.ImmutableKeys`, so `NodeQueryFor` honors `@writeOnce` even in the documented streaming call shape that passes a nil schema type — which previously got the mutable shape and silently overwrote every `@writeOnce` property on each re-ingestion MERGE.
- **Breaking change — `BuildBatchNodeMergeQuery` reads merge keys from a `key_`-prefixed row entry.** The emitted template now matches on `row.key_<name>` rather than `row.<name>`, and `Adapter.BatchNodeQueries` builds its rows to match, so the pair stays consistent and callers using the adapter entry point are unaffected. A caller using the exported builder **and** assembling its own rows must add the prefix. The prefix is what the single-node builder has always used for its parameters (`$key_<name>`); the batch row lacked it, so merge keys shared one namespace with `props` and `update_props` and a type whose primary key was itself named `props` or `update_props` — both legal DSL property names — had its key value overwritten by the property map, making every MERGE in the batch match on a map. That path became reachable without any caller opt-in once `@writeOnce` began selecting the split shape on its own.
- **Breaking API change — `DiffConstraints` and `DiffIndexes` take an `*OwnedLabels`, not a schema name.** `Adapter.OwnedLabels(ctx, s)` returns the exact set of labels the adapter emits for a schema — the same walk the emitters use — and both diff entry points scope themselves to it. Ownership is set membership rather than a rule applied to each remote object's label. This is breaking for `DiffConstraints` (`DiffIndexes` is new at v0.9.0 and unreleased); the CLI computes the set once and passes it to both halves.

  The change is not a refinement of the previous prefix test but a replacement for it, because no such test can be correct. `Adapter.Label` composes a label from a caller-configurable prefix and separator around two sanitized free-form names and is not invertible: a prefix test claimed a sibling schema's objects (`app` claiming everything under `app__legacy` and `app__Core`), anchoring the segment after the prefix still claimed any sibling whose next segment started uppercase, and any anchoring at all was defeated by `WithLabelSeparator("")`. Under set membership none of those inputs matter, and an empty schema name — where `Label` emits bare, unnamespaced labels — owns exactly the schema's own labels rather than either nothing or the entire database.

- **Behavior change — a remote constraint the schema could not have declared is ignored.** `DiffConstraints` now applies the declarability filter its index counterpart already had: relationship constraints (for which `LabelsOrTypes` holds a relationship type, not a label) and node constraint kinds the DSL cannot express are no longer reported as schema-owned orphans to drop, which was drift no schema edit could resolve.

- **Behavior change — desired objects pair with remote ones in three phases.** Both diffs match on name-and-identity together, then on identity alone, then on name alone. Previously, two remote objects sharing one identity (the schema's own plus an operator's ad-hoc definition) were paired positionally, so the classification depended on the order `SHOW INDEXES` / `SHOW CONSTRAINTS` returned rows in — and because those order by name, the diff routinely named the schema's **own** object as the one to drop. A name match whose definitions disagree is reported as drift rather than create-plus-drop: emitted statements carry `IF NOT EXISTS`, so re-creating under a name the database already holds silently does nothing and the plan never converges. Identity outranks name so that a remote object which exactly realises a declaration is not displaced by one that merely holds its name — otherwise the index actually serving the queries is the one the plan drops. A desired index whose name is held by a kind the DSL cannot express (FULLTEXT, TEXT, POINT) is likewise reported as drift naming the holder, since a CREATE under that name would be a permanent no-op.
- **Behavior change — a constraint the server will not fully describe is `Unverified`, not matched.** A TYPE constraint whose enforced type the database does not report (Neo4j < 5.9, or any driver path omitting the column) previously folded into `Match`, so `yammm neo4j diff` exited 0 on a genuinely drifted database. It now lands in the new `Unverified` bucket and exits **3** (`ExitRuntime`), matching how the index half already treated an unreadable vector configuration. Constraint or index drift still outranks it, exiting 1.
- **Behavior change — an index in a non-serving state is reported.** `SHOW INDEXES` lists a `FAILED` index with every column matching its declaration while it serves nothing, so a definition-only comparison called it in sync. A `FAILED` index is now **drift** (drop and recreate); a `POPULATING` one is **unverified** (transient). An unreported state is still treated as online, so older servers and hand-built records are unaffected.
- **Behavior change — colliding index names are disambiguated, not rejected.** The readable index name joins label and property names with underscores, and property names may themselves contain underscores, so `@@index(a, b_c)` and `@@index(a_b, c)` render identically — as do an `a_b` property on type `Item` and a `b` property on type `Item_a`. This was reported as an error; because index emission is all-or-nothing, one such pair suppressed **every** index in the schema and left the user renaming a domain property to get any DDL at all. Colliding names now receive a short deterministic digest suffix. Only names that would actually clash are suffixed, so every other index keeps its readable name, and pairing falls back to semantic identity when a name does not match, so an existing remote index is still recognised after a name changes.
- **Behavior change — `IndexesForSchema` returns nil for a schema with no index annotations.** It previously returned a non-nil, zero-length slice while `IndexesStructured` returned nil, so a caller distinguishing nil from empty got opposite answers from two entry points documented as differing only in shape.
- **Behavior change — MERGE keys are coerced like properties.** Every write entry point (`NodeQueryFor`, `BatchNodeQueries`, `EdgeQueryFor`, `EdgeQueriesFor`, `BatchEdgeQueries`) now binds its merge keys and relationship endpoint keys as the driver-native types the corresponding properties are stored as, using the constraint `ShapeForSchema` records for each primary key. `$props` was always coerced and the keys were not, so for a transforming kind — `Date`, `Timestamp`, `Float` — the MERGE matched on one representation while the SET wrote another: a `Date` primary key matched no stored node, and **every re-ingestion inserted a duplicate**; an association to such a type matched nothing and the edge was silently absent, with `matched_rows` returning a legitimate-looking 0. Affects only schemas with a non-`String`/`Integer`/`UUID` primary key. A hand-built `NodeShape` carries no key constraints and passes values through unchanged, as before. New failure mode: an uncoercible key value is now an error from the query builder rather than a silent mismatch at the server.
- **Breaking API change — `ParamTypesForType` no longer emits merge-key entries; `ParamTypesForMergeKeys` does.** One `ParamTypes` cannot describe both shapes: in a flat row `key_id` is a property so named, while in `BuildBatchNodeMergeQuery`'s row shape the same spelling is the merge key for `id` and the properties live nested under `row.props`. Emitting both meant a declared property named `key_<pk>` silently took the merge key's constraint, or the reverse. `ParamTypesForType(t, prefix)` is now what it was at v0.8.0 — one entry per property — except that it walks the **merged** property set, so an inherited property is covered. `ParamTypesForMergeKeys(t, prefix)` covers the primary keys under the `key_` namespace: prefix `""` for `BuildNodeMergeQuery`'s `$key_<pk>`, `"rows"` for `BuildBatchNodeMergeQuery`'s `row.key_<pk>`. Merge them with `maps.Copy` when the caller's own map carries both. Breaking only against this branch's unreleased shape; v0.8.0's `ParamTypesForType` emitted no merge-key entries either. Callers going through the adapter's write path need none of it — those coerce their own keys.
- **Behavior change — `DiffConstraints` declarability is edition-aware.** Under `WithEdition(Community)` the emitter produces UNIQUE alone, so the diff now also treats a remote NOT NULL or TYPE constraint as a kind this configuration cannot declare. Both sides of the comparison are filtered by one list. Previously the desired side was filtered and the actual side was not, so running `yammm neo4j diff --edition community` against an Enterprise-provisioned database made **every** NOT NULL and TYPE constraint an unmatched orphan and printed it as a drop — a plan whose application removes every required-property and property-type guarantee in the database.
- **Bug fix — the uniqueness constraint type is recognised on every supported server generation.** Neo4j renamed the node uniqueness constraint type that `SHOW CONSTRAINTS` reports: 5.x yields `UNIQUENESS`, 2026.x yields `NODE_PROPERTY_UNIQUENESS`, aligning it with the `NODE_PROPERTY_EXISTENCE` and `NODE_PROPERTY_TYPE` spellings the server has always used. The adapter compared the reported string against its own `UNIQUENESS` spelling, so against a 2026.x server **every UNIQUE constraint yammm emits misreported**, in two places. `DiffConstraints` found the remote constraint undeclarable and excluded it, then found the desired constraint's name taken and reported the schema's **own, correct** constraint as drift with "drop it before this constraint can be created" — under `--edition community`, where UNIQUE is the only kind emitted, that was the entire plan. `InferSchema` marked no primary key from such a constraint, so `yammm neo4j introspect` scaffolded a schema that fails to load on `E_NO_PRIMARY_KEY`. Both spellings are now folded to one before any comparison; `RemoteConstraint.Type` still carries exactly what the server reported, because drift messages echo it. This is a fix to behavior shipped in v0.8.0 and earlier, not to anything new at v0.9.0. The integration suite runs against `neo4j:2026.05.0` and is green on both editions.
- **Additive API surface (`adapter/neo4j`) — comparison scope and constraint-name blocking.** `ConstraintDiffResult` and `IndexDiffResult` each gain an end-of-struct `Excluded int`, counting the remote objects that entered **no** bucket because the comparison had nothing to say about them: the schema owns no label they carry, or they are of a kind it cannot declare. It exists so "0 to drop" cannot be read as "the database is accounted for" — objects left behind by a type deleted or renamed since the last apply sit on a label no current type declares, and ownership derived from the schema cannot name them. `Adapter.DiffIndexes` gains a variadic `alsoBlocking ...RemoteConstraint` (mirroring `DiffConstraints`), because a NOT NULL or TYPE constraint has no backing index and so appears in no `SHOW INDEXES` row, while its name still occupies the namespace indexes and constraints share. `ConstraintKind` gains `String()`, matching `IndexKind`. Existing calls compile unchanged.
- **Additive CLI surface** — a new `yammm neo4j indexes <schema.yammm>` command emitting index DDL from a schema's annotations, and a `--indexes` flag on `yammm neo4j diff`. The three `neo4j` subcommands now share one flag definition, because `diff` computes its desired side exactly as `constraints` and `indexes` emit it and a flag one command has and another lacks is a plan reporting drift the operator never introduced: `--separator` and `--prefix` on all three, and `--named`, `--edition`, `--node-keys`, `--scalar-types`, `--required-only-types` on `constraints` and `diff`. `indexes` takes neither the edition nor the constraint-shape flags — range and vector indexes are core query features on both editions, so there is nothing to gate. Outside the formally-versioned surfaces; noted for completeness.
- **Breaking CLI-behavior change — `yammm neo4j diff` now diffs indexes by default.** Schema annotations give the schema a vocabulary for indexes (`@index`, `@@index`, `@vector`), and `neo4j diff` compares them the way it has always compared constraints: an index in the database that the schema does not declare is reported as a **drop**, and drift, creates, and drops all fold into exit code 1. An invocation that previously exited 0 against a database carrying an operator- or pipeline-created index on a schema-owned label now exits 1. This is drift by the feature's definition — the remedy is to declare the index, and drops are reported, never applied — but it changes an existing command's exit code, so it is enumerated here.
  - `--indexes=false` restores exact constraints-only behavior, exit code included. Indexes are still **fetched** under it, because index and constraint names share one Neo4j namespace and the constraint half needs the index names to know whether a `CREATE CONSTRAINT` would silently no-op; the flag opts out of comparing indexes, not out of classifying constraints accurately. A server that cannot report indexes prints a warning and the constraint half degrades, but the flag never changes a constraint's classification by itself.
  - Only index kinds the DSL can express participate. `SHOW INDEXES` also reports FULLTEXT, TEXT, POINT, 4.x BTREE, and relationship indexes; those are ignored rather than reported as drops, since no schema edit could resolve them.
  - Two new non-zero outcomes, both meaning "the index half could not be completed", both exiting **3** (`ExitRuntime`) rather than reporting success for a comparison that never ran: an index whose vector configuration the server does not report is listed as **unverified** (never folded into the matched count), and a failed index introspection prints a warning and degrades to constraints-only. Constraint or index drift still outranks either, exiting 1.
  - A third exit-**3** outcome guards a failure that would otherwise be silent: an introspected constraint or index that parsed a **name but no type**. The parsers accept records from any source and return zero values for a field they cannot read, so a `type` column that stopped arriving — a rename, or a projection narrowed by a caller — would empty that field on every record, make every object undeclarable, and leave the command printing a confident plan built from a partial reading. Because the command knows which projection it issued, it treats a named-but-untyped record as a broken read: it names the count and the query on stderr and reports no comparison at all. A record whose type is present but *unrecognised* is a different case and is unaffected — that is an undeclarable kind, which the diff already accounts for.
- **Behavior change — CLI commands now print warnings, from every phase.** `cli.RenderResult` previously rendered only when a result carried an error, so a warnings-only result printed nothing in any command, `yammm validate` included; nine of the ten schema-loading commands additionally reached the renderer only on failure. Both are fixed: every command renders whatever it produced, at any severity, to **stderr**. Exit codes are unchanged (a warning is not a failure) and no command's stdout contract is affected. This is what makes `W_ANNOTATION_SHADOWED` — the only signal that a subtype re-declaration dropped an inherited `@writeOnce` — reachable. **It also surfaces warnings that already existed but no command printed**, so an unchanged, still-passing input may emit new stderr output at v0.9.0. The full set:
  - A schema using `-_` in a constraint bound has always drawn a Warning-severity `E_INVALID_CONSTRAINT` ("minus sign before `_` (unbounded) has no effect").
  - `yammm snapshot verify` now prints the decoder's Warning-severity `E_SNAPSHOT_PATH_FALLBACK` (a provenance path that fails `path.Parse`) and `E_SNAPSHOT_UNSUPPORTED_HASH_ALGORITHM`, on an otherwise unchanged `.ys` file. With `--format json` it prints a wire object where it previously printed nothing.
  - `yammm export` from a `.ys` snapshot, and `yammm snapshot save --into`, print the same snapshot-decoder warnings. Both previously gated on error severity, so an operator could ship an export believing integrity had been verified when it had not.

  Library callers are unaffected throughout — the `Result` always carried these.
- **Behavior change — one diagnostic document per invocation.** A command now renders **exactly one** `diag.Result`: a phase whose diagnostics do not end the run folds them into the result the command reports last. This is a wire-contract fix for `--format json`, where every render writes one complete JSON document and two concatenated on stderr are not parseable — reachable as soon as load warnings became renderable, in any command that loads a schema and then does something else (`check`, `load`, `export`, `snapshot save`, `snapshot verify`, `neo4j diff`, `neo4j constraints`, `neo4j indexes`, `gen`). Text output is unaffected apart from ordering: previously-separate diagnostic blocks now render as one sorted block.
- **Behavior change — the issue limit retains the most severe issues.** `diag.Collector` dropped whatever arrived after its cap, regardless of severity. It now retains the `limit` most severe issues seen, ties broken by arrival order: at the cap, an incoming issue more severe than the least severe stored one takes its slot. `Result.DroppedCount` still reports seen-minus-retained and the severity gates were always seen-based, so `OK`/`HasErrors`/`SeverityCounts` are unchanged; what changes is **which** issues a truncated `Result` can enumerate. This closes a starvation path the annotation stream opened — `W_ANNOTATION_SHADOWED` is collected during inheritance linearization, ahead of every error-producing completion phase, so a schema with enough shadowed annotations filled the default 100-issue budget with warnings and stored none of the errors explaining why it failed to load.
- **Behavior change — `E_PROPERTY_CONFLICT` deduplicated per conflict, with complete member pointers.** A property-inheritance conflict is now reported **once per conflict per affected type**, and re-detections through ancestors that merely carry the property forward no longer repeat the diagnostic (v0.8.0 emitted one per carrying ancestor). Each diagnostic now carries **related spans naming every declaration involved** — the full set that merged into the surviving definition, plus every declaration on the conflicting side — so one report never hides a declaration the fix must touch. The message format, primary span, code, and severity are unchanged, but the **declaration the message names on the surviving side is now the one that actually survived the merge**, which differs from v0.8.0 wherever a narrower declaration later took over as survivor. For a given schema the count is deterministic and never exceeds v0.8.0's. Scope and bounds:
  - The per-descendant repetition is retained: each affected subtype re-detects and reports the clash independently, so the failure surfaces at every type it breaks.
  - Grouping is first-fit, so with three or more mutually-tangled same-name declarations the report count depends on `extends`-clause order: deterministic for a given schema, but a permutation can group the same declarations differently and report a different number. Every grouping is sound either way — each report names a genuinely unmergeable pair, and no report ever absorbs a conflict incompatible with the one it names — so the order affects how finely conflicts are split, never whether one is reported.
  - **This affects schemas using no annotations at all** — any load failing on property-inheritance conflicts can report fewer diagnostics than v0.8.0, each carrying more location detail. Loads that pass are byte-identical; the change is confined to loads that already fail.
- **Behavior change — `E_RELATION_COLLISION` deduplicated per collision, with complete rival pointers.** Matching the property-conflict change above: a relation collision is reported **once per collision per affected type**, so ancestors that merely carry the relation forward no longer repeat it (v0.8.0 emitted one per carrying ancestor), and two ancestors declaring **structurally identical rivals** now draw one diagnostic rather than one each — a single edit to the surviving declaration resolves both. Each diagnostic gains **related spans naming the surviving declaration and every rival**, so the collapse never hides one. Rivals that are not structurally equal remain separate diagnostics. Message format, primary span, code, and severity are unchanged, and this affects only loads that already fail.
- **Breaking schema-loading tightening — a property annotation must be on its property's line.** `@name` decorators are property-**trailing** and the grammar does not treat line breaks as significant, so an annotation written on its own line binds to the property **above** it — while a reader coming from a prefix-decorator language (Python, TypeScript, Java) means the property **below**. Nothing distinguished the two readings: the schema loaded clean and the wrong property carried the marker into the emitted store DDL, so `@index` intended for one column indexed another and `yammm neo4j diff` reported the intended index as missing. Such an annotation is now `E_INVALID_ANNOTATION`, naming the property it actually attaches to and pointing at `@@name` for a type-level annotation. Same-line annotations — one or several — are unaffected, which is every form `yammm fmt` produces. Justified under the amended rule (a): the newly-rejected shape is enumerated here, and it never meant what it appeared to mean.
- **Behavior change — `E_PROPERTY_CONFLICT` / `E_RELATION_COLLISION` omit related locations that have no span.** A related entry without a location rendered as a bare `note:` line pointing nowhere — one per member, so a multi-member clash produced a stack of identical, information-free lines — while the LSP dropped such entries entirely, leaving the two surfaces disagreeing about the diagnostic's content. They are now omitted at the source. Affects only `schema.Builder`-constructed schemas, which carry no spans.
- **Bug fix — `Annotation` identity is injective across the name/argument boundary.** The internal identity key that backs duplicate detection and inherited-annotation dedup did not delimit the annotation name from the first argument's encoding, so a name spelled to imitate that encoding collided with an unrelated annotation — reporting a genuine annotation as a duplicate and, on a subtype, letting only one of two distinct composite indexes survive into the merged view. Reachable only through `TypeBuilder.WithTypeAnnotation` / `WithPropertyAnnotation`, which take the name as a plain string; the DSL grammar cannot spell such a name.
- **Bug fix — a diagnostic echoing a quoted annotation argument keeps the source's quote style.** The yammm lexer accepts both `'` and `"`, but the echo re-quoted through `strconv`, so a single-quoted argument was reported back to the user in double quotes.
- **Bug fix — a rejected property re-declaration no longer suppresses annotations for its subtypes.** A re-declaration that drew `E_PROPERTY_CONFLICT` still recorded its annotation drop, so every subtype derived an `E_INVALID_ANNOTATION` disagreement from a declaration the same load had already rejected — telling the user to edit the subtype when the only real fix was at the rejected declaration.
- **Behavior change — `schema.Constraint.Equal` is now reflexive for unresolvable alias chains.** An `AliasConstraint` whose chain does not bottom out in a terminal constraint (an unresolvable datatype, or a cycle) previously compared **unequal to itself**, because equality could not be decided structurally and the undecidable case returned false unconditionally. Such aliases now compare equal when they reference the same datatype — which makes `Equal` reflexive, as every caller assumes — while aliases naming *different* unresolvable datatypes stay unequal, preserving the "cannot determine" policy. Reachable through `schema.Builder`, which accepts an alias-of-alias datatype the DSL grammar cannot express; there, inheritance merging previously reported a property as conflicting with **its own declaration** (`from A and A`), once per carrying ancestor. Schemas whose datatypes all resolve are unaffected, so no schema that loaded clean at v0.8.0 changes behavior.
- **Formatter and editor tooling** — `yammm fmt` (and the LSP's formatting) handle annotation spacing: no space after the `@` / `@@` sigil, and none between an annotation name and its argument list (decided from token-stream state, since that same name-then-`(` pair is a relation multiplicity elsewhere and must keep its space). A line beginning with a sigil is treated as its own declaration rather than a wrapped continuation of the line above. The LSP adds annotation-name and argument completions plus registry-backed hover, and the VS Code grammar highlights the sigils. Because annotation text could not previously parse, **no previously-valid schema formats differently**. Outside the formally-versioned surfaces; noted for completeness.
- **No hash or wire migration.** Annotations are deliberately excluded from `schema.StructuralHash` (`StructuralHashVersion` stays `1`): they drive downstream store DDL and write shape, not what instance data is valid. A schema that gains its first annotation therefore hashes identically to v0.8.0, so every persisted `.ys` snapshot header hash, every snapshot cross-check, and every `gogen` `SchemaHash` constant stays valid.

### Instance-layer edge validation

- **Breaking schema-loading tightening — edge-property datatype references now validated at load.** Association edge properties join the resolution and validation coverage type properties have had since v0.7.0. Three previously-silently-loading schema shapes are now rejected:
  1. An edge property typed by an **undeclared datatype** (`tag Mystery` with no `type Mystery = ...`) — now `E_UNKNOWN_TYPE` at load (previously loaded silently; the v0.7.0 unknown-property-datatype tightening did not reach edge properties).
  2. An edge property whose datatype alias resolves to **Vector** (`type Emb = Vector [3]` + edge property `e Emb`) — now `E_INVALID_CONSTRAINT`, closing the alias evasion of the Vector-on-edge ban (the direct form `e Vector [3]` was already rejected).
  3. An edge property whose datatype alias resolves to **List** (`type Lst = List <String>` + edge property `l Lst`) — now `E_LIST_ON_EDGE`, closing the alias evasion of the List-on-edge ban (the direct form was already rejected).
  Justified under the amended rule (a): the known consumer set declares no such shapes (grep-verified), and each newly-rejected shape is enumerated above.
- **Panic fix — `schema.StructuralHash` on datatype-typed edge properties.** Hashing a schema whose association declared a DataType-typed edge property panicked (`hashConstraint` reached the unresolved alias), crashing every hashing surface: `snapshot.Marshal` (`yammm snapshot save`), the snapshot decoder's schema-hash cross-check, `snapshot.SchemaHashMatches`, `gogen.Marshal` (`yammm gen --to go`), and `schema.Registry` re-registration. All now work. **No hash-migration concern:** affected schemas previously panicked before producing a hash, so no persisted hash, snapshot, or generated artifact changes meaning; schemas without datatype-typed edge properties hash identically to v0.8.0.
- **Validation loosening — datatype-typed edge-property values now validate.** The instance layer previously rejected every value of such a property (`unresolved alias constraint`); values now check and coerce against the resolved underlying constraint, exactly like datatype-typed type properties.
- **Validation loosening — relations declared on imported types and inherited cross-schema now validate.** The instance layer resolves association and composition targets by the completion-recorded absolute identity (`Relation.TargetID`) instead of re-resolving the declared target name entry-relatively. Previously-rejected valid data now validates: edges on imported types whose target is qualified by the declaring schema's own alias (`E_INSTANCE_TYPE_NOT_FOUND` before), compositions on imported types (owner-name lookup failure before), and both member kinds inherited by an entry-schema type from a cross-schema parent. `instance.SchemaBuilder` (`EdgeTo`/`EdgeToWith`/`Composed`) gains the same reach. The public string-tag contracts of `Validate`/`ValidateOne`/`ValidateForComposition` are unchanged (entry-relative, as documented).
- **Data-validation tightening — cross-schema name shadowing no longer misvalidates edge data.** When an entry schema declares a type whose bare name shadows the declaring schema's target of an imported type's relation, the FK block was previously validated against the *entry's* shadowing type: correct-keyed data was falsely rejected and wrong-keyed data **falsely accepted** (an integrity hole caught only later, at graph resolution, blamed elsewhere). Wrong-keyed edge data that previously passed per-file validation (`yammm check`, `instance.Validate*`) is now rejected with the FK diagnostics of the true target; the composition duplicate-child-PK check likewise now runs against the true child type instead of being silently skipped on a shadowed or unresolvable name.
- **Additive API surface (`schema`)** — `Schema.Closure() []*Schema` (the schema plus its transitive import closure: breadth-first over imports in declaration order, deduplicated by SourceID, deterministic, defensively copied) and `Schema.TypeByID(TypeID) (*Type, bool)` (closure-wide lookup of the absolute type identities completion records). Both lazily computed and cached; safe for concurrent use. The three generator adapters' formerly-private closure walks (gogen, jschema, markdown) now consume `Closure()` — an internal consolidation with byte-identical generated output — and the instance layer consumes `TypeByID`. Justified under the pre-1.0 "additive API changes" rule.

The `.ys` wire format is unchanged at v0.9.0 (header `version` stays `2`), and no annotation state is persisted to it. Deferred-resolution behavior is preserved: a registry-less `schema.Builder` schema whose cross-schema relation target was never resolved (zero `TargetID`) falls back to the prior syntactic resolution path and its not-found error.

The fulltext-index annotation pair (`@fulltext` / `@@fulltext`), one diff behavior change it deliberately causes, binary version observability, and the version-lockstep release policy. Minor tier: the DSL and API surface is additive, and the behavior change is a tightening enumerated below. The `.ys` wire format is unchanged at `version: 2`, and — as with v0.9.0 — annotations stay excluded from `StructuralHash`, so a schema gaining its first `@fulltext` hashes identically.

Primary keys are allowed for both placements with no redundancy rule: a uniqueness constraint's backing index is a range index and cannot serve fulltext queries, so the `@index` sole-key rule does not transfer. `@@fulltext` rejects literal arguments; that rejection reserves a trailing string literal as the additive extension slot for a future analyzer option. Fulltext indexes emit for both editions. Analyzer configuration is a **documented known limit**: the schema cannot declare one, no `OPTIONS` clause is emitted, and the diff does not compare it — a remote fulltext index with a custom analyzer but matching (label, properties) is a Match.

- **The behavior change — the fulltext declarability flip.** Through v0.9.1 an owned `FULLTEXT` row was Excluded from the index diff; it is now a declarable kind, so an owned, *undeclared*, single-label fulltext row classifies as a **Drop**. Consequence: `yammm neo4j diff` (indexes are compared by default; `--indexes=false` opts out) against a database carrying operator-created fulltext indexes on owned labels flips from exit 0 to exit 1 — exactly the definition-drift authority the feature exists to provide. Downstream consumers migrating a hand-maintained fulltext registry must therefore adopt atomically: bump and annotate in one change, or every registry-created fulltext index reads as an undeclared Drop. **Multi-label** fulltext rows (`FOR (n:A|B)`) — a shape no per-type annotation can declare — stay out of declarability, identity pairing, and the definition-blocker map (they are counted in `Excluded`; the server creates a single-label declaration beside them), while their names still block every CREATE.

- **Version observability (`cmd/yammm`, `cmd/yammm-lsp`).** Both binaries now fall back from the ldflags-injected version to `debug.ReadBuildInfo`'s main-module version, so a plain `go install github.com/simon-lentz/yammm/cmd/...@vX.Y.Z` binary self-reports its tag instead of `dev`. Behavioral but strictly informative: only the `--version` output (and the LSP's logged version) changes, and only for builds that previously reported `dev` while knowing better. `(devel)` and versionless builds keep reporting `dev`.

The extension participates because its marketplace VSIX is not just grammar files: the publish workflow builds a per-platform `yammm-lsp` into every package, and the extension prefers that bundled server over a PATH install whenever `yammm.lsp.serverPath` is unset — so a marketplace republish is what keeps marketplace installs' language server current, and the extension version states which server the package carries. **The release's definition of done includes the tooling ship**: the release is complete only when `yammm-lsp` is released at the same tag and a reinstalled binary verifiably reports it — a stale LSP actively rejects the new grammar as `E_SYNTAX`, which is the observed failure mode this requirement closes — and when the VS Code extension is republished from the release tag, so the bundled server is built at that tag rather than left at the previous release's grammar.

The parse phase is about 65% of a load, so the end-to-end ratio is dominated by the parser and not by anything downstream. ## v0.12.0 under this policy

The pre-1.0 sweep release: the expression-contract decisions ratified after the built-in contract freeze, plus the SPEC corrections that pass surfaced, plus the `.ys` wire and identity fixes three review rounds found underneath them. Minor tier under the pre-1.0 rules on two independent grounds. It carries a **breaking public API change** — `graph.Snapshot` and the `graph.*Parts` structs are keyed by `schema.TypeID` rather than by type name, enumerated below under conditions (b)/(c) of the amended subtractive rule — and **five user-visible expression-language behavior changes** — the `TypeOf` vocabulary, the bracket-argument and else-less-ternary tightenings, the string-literal escape vocabulary, and List indexing with `Len` over a map — two of them tightenings where previously-accepted input now draws a diagnostic. Each is enumerated below with its blast radius. It is also a **wire migration release**: the `.ys` format moves to `version: 3` and the accept range to `[2, 3]`, so v1 documents are no longer read.

- **`TypeOf` reports the DSL type vocabulary.** The value was the Go `%T` string (`"int64"`, `"float64"`, `"bool"`, `"[]interface {}"`, and `"immutable.Slice"` for a list-valued property — the same value could report two names depending on how it arrived). It is now a closed vocabulary: `"nil"`, `"boolean"`, `"integer"`, `"float"`, `"string"`, `"list"`, `"map"`, `"pattern"`, `"timestamp"`, `"uuid"`, with `"unknown"` for any value outside it. The name comes from the **value**, not the declared property type: a `Timestamp`, `Date` or `UUID` property holding a string yields `"string"`, and only a `Timestamp` holding a Go `time.Time` yields `"timestamp"` or a `UUID` holding a `uuid.UUID` yields `"uuid"`. A `uuid.UUID` is `[16]byte`, so before `"uuid"` joined the vocabulary it reached the classifier's array arm and reported as `"list"`. Naming the declared type would require the constraint at the builtin, which the signature does not carry; the limit is documented in SPEC rather than engineered away. Any invariant comparing `TypeOf` output against a Go type name changes result. In-repo and known-consumer usage of `TypeOf` was zero at the decision; the vocabulary is enumerated in SPEC and pinned by the tracked contract corpus.

- **Extra bracket arguments draw an evaluation error.** `expr[a, b]` previously evaluated as `expr[a]`, silently discarding — and never evaluating — every argument after the first, while SPEC documented a range slice that did not exist. It now draws `E_EVAL_ERROR` (`slice access accepts exactly one index`). A tightening: no valid program can depend on the discard. Single-index behavior is unchanged, including out-of-range evaluating to `nil`.

- **The else-less ternary is rejected at load time.** `cond ? { x }` previously parsed and then drew `E_EVAL_ERROR` on every evaluation — both branches, always, since the evaluator requires three operands. The missing `:` is now `E_SYNTAX` (`expected ':' and an else branch in a conditional`) at schema load. A schema carrying the form stops loading, but no working schema breaks: the form could never evaluate.

- **String literals resolve the documented escape vocabulary.** The unquoter previously rebuilt every literal as a Go double-quoted string and delegated to `strconv.Unquote`, so three spellings SPEC has always documented drew `E_SYNTAX`: an unescaped `"` inside a single-quoted literal (`'a"b'`), the `\'` escape in either quote style (leaving no way at all to write an apostrophe in a single-quoted literal), and bare `\0`. A hand-rolled unquoter now resolves exactly the lexer's escape set (`\b \t \n \f \r \0 \xHH \uHHHH \" \' \\`), so those spellings load. Mostly a loosening — previously-erroring input now loads — with **one value delta**: `\0` is no longer a Go octal prefix, so a literal like `"\012"` previously resolved to the single byte U+000A and now resolves to U+0000 followed by `12`. Malformed escapes (`\x` without two hex digits, `\u` without four, surrogate code points) still draw the same diagnostic with the same message text at every site: `unquote string: invalid syntax` as the cause at the schema-name, import-path, enum, pattern, timestamp and annotation sites, and `invalid string literal: invalid syntax` at the expression site, which supplies its own context and so reports the cause without the shared prefix. Consumers matching diagnostic text on the error path see no change. Reaches every unquote site: schema names, import paths, enum values, pattern values, timestamp formats, annotation string arguments, **and invariant-expression string literals**. The expression site was the last to route through the shared unquoter and had the sharpest symptom: it delegated to `strconv.Unquote` on the raw token, which reads a single-quoted literal as a Go *rune* literal, so **no single-quoted string of more than one character could be used in any invariant** — `! "m" name == 'abc'` drew `E_INVALID_INVARIANT`, as did the `\'` escape and bare `\0` there. Note the code at that site is `E_INVALID_INVARIANT`, not `E_SYNTAX`. **Invalid UTF-8** now resolves as `strconv.Unquote` resolved it — each bad byte becomes U+FFFD — so `\0` remains the only value delta.

- **Schema-aware float emission — `.ys` whole floats gain decimal form.** `snapshot.Marshal` now emits every value under a `KindFloat` constraint — node, edge, unresolved-edge, composed-child, and duplicate-section properties, `List` elements (aliases resolved at every level), and `Vector` elements — in a form carrying a float indicator: `float64(1860000)` writes as `1860000.0` where it previously wrote `1860000` and narrowed to `int64` on the next load. Behavioral rather than structural in its own right — it changes no field and any v2-era reader parses the new form losslessly (`immutable.NormalizeNumber` has always classified decimal forms as float) — though it ships in the same release as the `version: 3` migration below. **Healing**: an `int64` already narrowed by a prior round trip re-emits in decimal form on its next Marshal. Healing turns on **exact convertibility**, not magnitude — an integer heals when `float64(n)` converts back to `n` exactly, so `1e18` and every power of two beyond 2^53 heal where a plain 2^53 bound stranded them, while `MaxInt64` and `2^53+1` still pass through. **Every numeric value** a caller can place under a float-bearing constraint is covered, not only `float64` and `int64`. `float32`, every sized int and uint, named types over them, and `encoding/json.Number` all reach the emitter and must not narrow. They arrive through `graph.RebuildSnapshot` or a test helper, and a `json.Number` also arrives from a caller who decoded with `UseNumber` or from a value `immutable.NormalizeValue` left unconverted past its depth cap. A `json.Number` is classified by `immutable.NormalizeNumber`, the rule the reader itself applies, so one literal cannot mean a float on the way out and an `int64` on the way back in. A literal neither parser accepts passes through untouched, because inventing a value for it would write data the document never carried. A `float32` emits the shortest form that reads back as the same `float32`: `float32(0.1)` writes `0.1`, where widening to `float64` and formatting at 64-bit width spends 17 significant digits describing 32 bits of value. Vector embeddings are the natural `float32` shape, so that width is kept at every element of every embedding. Marshal output is a fixpoint — `Marshal(Load(Marshal(x)))` is byte-identical to `Marshal(x)` **for any document Load accepts** — and `snapshottest.DiffSnapshots` drops its mixed int64/float64 tolerance: round trips now compare exactly, dynamic type included, and the duplicates section compares full instance trees rather than bare identities. Byte movement: integrity hashes of float-bearing documents change on re-marshal; `UpdateMetadata` keeps a legacy body verbatim while `Marshal(Load(x))` heals it — the one deliberate divergence between those two paths, recorded in the wire contract. Emission is unconditional; there is no opt-out flag, because a flag would preserve the ambiguity the change removes. A NaN or Inf under a float-bearing constraint errors from the wire-value marshaler rather than from `encoding/json` directly, so the message differs in prefix; validation rejects both at `coerceFloat`, so only a caller-assembled snapshot reaches it. A `Vector` or `List` position is reached through **any slice or array**, not `[]any` alone, so a caller-assembled `[]byte` under such a constraint now emits as an array of decimals where `encoding/json` previously rendered it as a base64 string — the array being the shape the declared type calls for.

- **A composed child keeps its type identity across a `.ys` round trip.** The wire omits `type_id` for a child the parent relation identifies, and the decoder recovered such a child's type from the **relation name** — so any relation named differently from the type it targets silently replaced the child's identity on load (`Part` under a `PARTS` relation loaded back as type `"PARTS"` with a zero TypeID). The decoder now recovers the child type through the parent type's relation target, and **an explicit `type_id` is authoritative** — resolved by schema path *and* name, never overridden by the relation target — with the relation name only as a last resort; `marshalComposedChild`'s omission rule was restated to match that recovery. **Pre-existing, not introduced here** — the branch's own fixpoint pin passed over it because a `!typeID.IsZero()` guard suppressed the empty `"type_id":{"schema_path":"","name":""}` object the second marshal would otherwise have emitted. That guard stays and still prevents the contentless object.

  The recovery rule's first form let the relation target win whenever the two agreed **by name alone**, which silently rebound a child to the wrong schema in both directions wherever two schemas declare a type of the same name — the shape a generated round-trip corpus reproduced and no hand-written fixture had. A composed child's properties are also encoded under the child's **own** type now, not the relation target's: encoding them under another type's constraints dropped float indicators and narrowed the values on the next load. Byte movement: a composed child whose type differs from its relation target carries a `type_id` it previously omitted or omitted wrongly, and one whose parent type does not resolve carries one it previously omitted.

- **A `.ys` document whose `type_id` contradicts its own tag form is reported.** The load-time cross-check compared the persisted type name alone, so a `type_id` naming a same-named type in a different schema was silently discarded. It now also compares the schema path **when that path resolves to a type**, drawing `E_SNAPSHOT_TYPEID_MISMATCH`; an unresolvable path stays silent, because it means the schema moved since the document was written rather than that the document is wrong. Before this release the code was emitted by one branch and referenced by no test anywhere in the tree.

- **A `.ys` document holding an instance of an imported type can be loaded.** `Marshal` writes the alias-qualified tag form (`base.Basin`) into the `types` array, and every decode-side type lookup used `Schema.Type`, a local-name-only map — so `Load` rejected the document its own `Marshal` had produced with `E_SNAPSHOT_UNKNOWN_TYPE`, and no cross-schema snapshot round-tripped at all. All four decode-side lookups (types-array validation, instance resolution, composed children, the duplicates section) now resolve the tag form. **Pre-existing**; no test constructed a cross-schema snapshot, so nothing caught it. A fix, not a break: documents that previously failed to load now load, and no document that loaded before changes meaning.

- **A `.ys` document holding a transitively imported type can be loaded, and a persisted `type_id` is authoritative everywhere.** The tag form a document carries is a *name*: bare for a local type, alias-qualified for a directly imported one. A type the entry schema reaches only through an intermediate import has no alias to qualify with, so its tag is a bare name that resolved against no schema — `Marshal` wrote `"types":["Probe"]` and `Load` rejected it with `E_SNAPSHOT_UNKNOWN_TYPE`, so no such document round-tripped at all. Two changes close that. The types array now accepts a bare name declared anywhere in the import closure — a pure existence check, never a binding, because a name two schemas declare resolves to neither. And every position that persists a `type_id` now resolves from it first and falls back to the tag: root instances, composed children, and **the duplicates section, which persisted an identity and read it back with nothing**. The emitter changed with them — `resolveWireType` prefers the caller's identity over the tag form, so an instance whose name and identity disagree no longer has its properties encoded under whichever type the name reached. **Byte movement**: a duplicate or root instance of an imported type now encodes under its own type's constraints, so its float-bearing values gain the float indicator they were losing and integrity hashes of such documents change on re-marshal. **Pre-existing**; the round trip was never exercised across a transitive import.

- **An ambiguous legacy document loads with a Warning instead of being rejected.** When a document's tag form resolves to one type and its own persisted `type_id` names a same-named type in another schema, the two disagree only because the tag form cannot express the difference — the document is ambiguous, not wrong, and it carries the identity that settles it. That case drew `E_SNAPSHOT_TYPEID_MISMATCH` at Error severity and `Load` returned no snapshot; it now draws the same code at **Warning**, the persisted identity decides, and the document loads. A `type_id` naming a *differently* named type is still a contradiction and still an Error. The duplicates section drew neither before and now draws both. Related: a composed child whose persisted schema path no longer resolves — the shape a document takes after its schema moved — now falls back to resolving the persisted *name* instead of yielding a zero identity that cannot be written back at all.

- **Additive: `schema.TagForm` and `W_SNAPSHOT_AMBIGUOUS_TYPE`.** `schema.TagForm(s *Schema, id TypeID) string` renders a type identity as the name a snapshot carries. It is the single implementation of a rule that had three copies drifting apart in four ways, and it is what callers use wherever output needs a name rather than an identity. `W_SNAPSHOT_AMBIGUOUS_TYPE` (Warning) reports a legacy type name that more than one schema in the import closure declares; `E_SNAPSHOT_UNKNOWN_TYPE` gains a Warning-severity emission for a legacy name that no closure schema declares.

- **Importing a snapshot keeps every instance of a transitively imported type.** `graph.NewFromSnapshot` and `graph.NewBatchAssemblerFromSnapshot` filed instances by resolving the tag form, which misses a bare transitive name — and the miss was a silent `continue` that **dropped every instance of the type**. Instances are now filed by the identity each one carries, which the re-keyed `Snapshot` hands them directly. The path was unreachable while `Load` rejected such documents outright; fixing the load is what makes it reachable. Also: `E_UNRESOLVED_REQUIRED`'s `json_field` detail is populated for imported source types, where a local-name-only lookup left it empty for exactly the types a cross-schema document holds.

- **BREAKING — `graph.Snapshot` is keyed by type identity, not by type name.** A type name is a *rendering* of `schema.TypeID`: bare for a local type, alias-qualified for a directly imported one. It cannot name a type reachable only through an intermediate import — that renders bare — and it renders two same-named types in different schemas identically. Keying by it merged them: `Graph.Snapshot()` overwrote one group of instances with the other **before `Marshal` ran**, so a lossless wire would have described data the snapshot no longer held. Every position that must denote a type exactly now takes an identity. **Changed signatures**: `Snapshot.Types() []schema.TypeID`, `Snapshot.InstancesOf(schema.TypeID)`, `Snapshot.Instances() map[schema.TypeID][]*Instance`, `Snapshot.InstanceByKey(schema.TypeID, string)`. `Snapshot.AllInstances()` is unchanged in signature. **Changed field types**: `SnapshotParts.Types` and `SnapshotParts.Instances`; `EdgeParts.SourceType` / `TargetType`; `DuplicateParts.Type`; `UnresolvedParts.SourceType` / `TargetType`; and the public `UnresolvedEdge.TargetType`. That last one is not a display field — `graph.NewFromSnapshot` reads it back to build the pending-edge key that later resolves an arriving target, so a name there would be re-resolved and could bind to the wrong type. Callers needing a name for output take it from the new `schema.TagForm`; the three adapter writers and the CLI exporter do exactly that. **Byte movement**: `Types()` sorts on `TypeID.String()` (schema path, then name) rather than on the tag, so **cross-schema documents change their `types`-array order** and with it their integrity hashes. Single-schema documents are unaffected — one path prefix leaves the relative order identical, and no committed golden moved. Permitted under the amended pre-1.0 rule (a): the single external consumer pins an older release and migrates on its own schedule.

- **BREAKING — the `.ys` wire format moves to `version: 3`, and the accept range to `[2, 3]`.** v2 carried type identity twice: a tag-form *name* at the `types` entry, the instances-map key, `edge.target_type`, `duplicate.type` and the unresolved record's source and target, plus an *optional* per-instance `type_id` object written only where three hand-maintained omission predicates said the name would not recover it. The name is lossy — it cannot express a transitively imported type, and two same-named types in different schemas render identically — so three consecutive review rounds found defects in the predicates that invert it. v3 carries identity **once, losslessly**:

  - **`types` is a table of objects**, each `{"schema_path", "name", "tag"}`. `schema_path` + `name` is the identity; `tag` is the name a reader renders, carried rather than recomputed so `Instance.TypeName()` round-trips verbatim instead of passing back through the rule that was wrong three times.
  - **`instances` is an array parallel to `types`**, so `instances[i]` holds the root instances of `types[i]`. Identity stops flowing through a map key, which is what closes the same-tag collision: a local `Part` and a transitively imported `Part` are two rows, not one key. The types/instances cross-check becomes a length comparison.
  - **Every other type reference is a table index**: composed children, `edge.target_type`, `duplicate.type`, and the unresolved record's `source_type` and `target_type`. The per-instance `type_id` object is **removed entirely** — a v3 writer omits nothing, so the predicate class is deleted rather than corrected a fourth time.
  - **The table denotes every type the document references, not only those holding instances.** An unresolved edge's target type has no instance by definition and still takes a row; its `instances` entry is an empty array. `SnapshotInfo.Types` and `HeaderInfo.Types` therefore list types a v2 document would have omitted. Both keep their `[]string` type and carry each row's `tag`, so no consumer signature changes; `SnapshotInfo.InstanceCounts` accumulates per tag rather than assigning, because two rows can render one name.
  - **v1 documents are no longer read.** `MinReadableVersion` rises from 1 to 2. v1 predates the single external consumer's adoption, which began at a v2-era pin, so no consumer document is v1 — but any archived or hand-written v1 file now draws `E_SNAPSHOT_UNSUPPORTED_VERSION` where it previously loaded. Breaking, and enumerated as such.
  - **Asymmetric-reader semantics, matching the v1 → v2 precedent.** A v3 reader (v0.12.0+) accepts v2 documents and resolves their identity on the way in. A v2 reader (v0.11.0 and earlier) rejects a v3 document cleanly through the unknown-version path rather than misreading the new sections. **The migration is one-way and one-pass**: `Load` a v2 document and `Marshal` it and the result is v3 carrying the identity the v2 document meant — including a transitively imported type its tag form could not name. Re-marshalling therefore **freezes the reader's resolution**, which is why the legacy read path resolves identity-first; `UpdateMetadataOrReMarshal` is the migrating path, and `UpdateMetadata` is not (see below).
  - **Byte movement, both directions.** Cross-schema documents **shrink substantially**: one table row replaces N per-instance `type_id` objects, each of which embedded the writer's absolute schema path. Single-schema documents **grow slightly** — roughly ten bytes per composed child, which v2 left implicit and v3 states. Every integrity hash changes; that is inherent to a format bump.

- **Additive: composed-child duplicates carry their parent's coordinates.** `graph.Duplicate` gains `Parent *Instance` and `Relation string`; `graph.DuplicateParts` gains `ParentType`, `ParentKey` and `Relation`; the v3 duplicate record gains the matching `parent_type`, `parent_key` and `relation` fields. This fixes a document `Marshal` wrote and `Load` refused: a composed child never appears in the instances section, so a duplicate naming one had no entry for the reader's existence check to find, and both `Load` and `Verify` rejected with `E_SNAPSHOT_DANGLING_REFERENCE` — losing the whole graph, not only the duplicate record. `graph.RebuildSnapshot` hit the same wall from the other side with a Fatal `E_INTERNAL`. Both now resolve the conflict by walking parent → relation → child key. Any pipeline that reached a composed-child primary-key collision could previously write a `.ys` it could never read back.

- **`UpdateMetadata` preserves the input document's format version, and refuses documents no read path accepts.** The metadata fast path rebuilt the header through helpers that wrote the writer's current version as a literal while reusing the body verbatim. That was harmless while a v1 body was a valid v2 body; under the v3 bump it would stamp `version: 3` onto a v2 body and the next reader would take the v3 path over v2 bytes. The version is now a parameter: `Marshal` passes the current version, `UpdateMetadata` passes the one it read. Separately, `UpdateMetadata` tested only the error `decodeHeader` returns and never its collected diagnostics, so it accepted three shapes every read path refuses — an out-of-range version, `features: null`, and an unrecognized feature entry. It now returns those diagnostics instead of rewritten bytes, and `UpdateMetadataOrReMarshal`'s `Load` fallback refuses them too. The hash-algorithm mismatch stays a Warning and still passes. `UpdateMetadata` remains a header rewrite and never a migration.

- **Indented output nests the body sections by the caller's indent.** `Marshal` passed a hardcoded two-space prefix to the body-section encoders while the header nested by the configured indent, so `WithIndent("\t")` produced a document whose header used tabs and whose `types`, `instances` and `diagnostics` sections used two spaces then tabs. Both are now the caller's indent. Compact output is unaffected; indented output changes bytes and therefore its integrity hash.

- **A legacy `.ys` document binds a type name it cannot resolve against the import closure, and says so.** The v2 wire names types where it needs to denote them, so `Load` now resolves an unresolved-edge tag the entry schema cannot name against the whole closure: a name declared exactly once binds; a name declared in several schemas binds the first in closure order and draws the new `W_SNAPSHOT_AMBIGUOUS_TYPE` (Warning); a name declared nowhere drops the record with an `E_SNAPSHOT_UNKNOWN_TYPE` **Warning** where it was previously dropped in silence. The rule lives in the reader because that is where the wire is decoded; nothing downstream re-derives a type from a name. Related: `graph.Snapshot` instance groups are filed by each instance's own identity, so importing a snapshot no longer drops every instance of a transitively imported type on a lookup the entry schema cannot make.

- **A registry-less `schema.Builder` rejects dangling qualified references.** A qualified reference (`Extends`, a relation or composition target, or a qualified datatype constraint) whose alias names no resolvable import previously deferred "to link time" when no registry was provided, sealing a schema that silently dropped its supertype, left a zero relation `TargetID`, or kept an unresolved primary-key type — even though no link step exists that could ever resolve it. It now draws `E_UNKNOWN_TYPE` and nils the schema, exactly as the same reference does with a registry present. **Breaking** for any consumer building registry-less schemas with qualified references (none is known; the state was production-unreachable — rdata builds exclusively via `Load`). This reverses the registry-less half of the v0.7.0 strictness note's second `Builder` carve-out; the declared-but-failed-import deferral (the root cause already reported) is unchanged. Consequence: a sealed schema carrying a dangling or deferred reference is no longer obtainable through any public entry point, so the downstream defensive arms (the adapter's emission-time index re-checks, the instance layer's entry-relative target fallback) become pure defense in depth — their codes (`E_NEO4J_UNKNOWN_PROPERTY`, `E_NEO4J_INVALID_INDEX_TARGET` via this route, `E_INSTANCE_TYPE_NOT_FOUND` via the fallback) stay registered and the code stays, but no public construction reaches them.

- **Cost — `format.TokenStream` stops lexing the source twice.** The formatter needs both the un-elided token stream and the node tree; it previously ran a full second lex for the stream. An internal single-pass entry point now returns both views from one lex, cutting formatter time by 29% on the tracked fixture corpus and 41% on a 200-type synthetic schema (Apple M2). Both figures are derivable from the committed benchmarks rather than a one-off comparison: the removed work is exactly one `parse.Lex`, so `BenchmarkLexOnlyCorpus` / `BenchmarkLexOnlySynthetic` measure it directly against `BenchmarkTokenStreamCorpus` / `BenchmarkTokenStreamSynthetic`. Output bytes are unchanged — the returned stream is pinned equal to the standalone lexer's over every tracked fixture — so this is purely a performance change on the `yammm fmt` and LSP formatting paths.

- **A `List`-typed property is indexable, and `Len` counts a map.** `expr[i]` handled `[]any` and `string` but not `immutable.Slice` — what `Value.Unwrap` returns for a collection — so indexing any List property was an evaluation error against the SPEC's own Indexing section. `Len` had the mirror gap: a map value is `immutable.Map[string]`, a struct, which its `reflect.Map` arm never matched, so `$self -> Len` errored while `$self -> TypeOf` already answered `"map"`. Both are fixes; no working expression changes meaning. The empty index list `expr[]` keeps drawing an evaluation error, now worded in the same user-facing vocabulary as the two-index case. The List arm bounds-checks in `int64` like its `[]any` and `string` siblings, so an index beyond `int32` range yields `nil` rather than wrapping into range on a 32-bit build — unobservable on every platform this project ships, and relevant only to a consumer building 32-bit.

- **The LSP canonicalises every path the same way.** Four hand-written canonicalisers — in the analyzer and at three workspace sites — differed from each other and from the schema loader's own `makeCanonicalPath`: some resolved symlinks before cleaning, where the loader cleans first, and some skipped making the path absolute. For a path containing `..` across a symlink the two orders land on **different files**, not two spellings of one. All of them now route through a single helper mirroring the loader's order (absolute, then cleaned, then resolved, keeping the cleaned form when resolution fails, which a virtual markdown source and a deleted file both need). User-visible where a workspace root arrived in a form the document paths did not match: the root registered under a path no document matched, so `FindModuleRoot` fell back to the file's own directory. **No client-visible diagnostic misposition was fixed** — an earlier framing of this work claimed one, and driving the real server with the change reverted produced identical, correct columns; what changed is the robustness of the Analyzer's own API and the canonicalisation ordering.

- **SPEC corrections from the contract-freeze pass.** Three false claims corrected — property lookups documented as strict (they are statically checked at load; declared-but-absent evaluates to `nil`), the `expr[start, end]` range slice (never implemented; see the tightening above), and "ordered comparisons evaluate to false for incomparable operands" (supported types are totally ordered by strata) — plus nine documented gaps closed (list `+` concatenation, `Substring`'s one-argument/negative/clamping forms, the empty-collection results table, `Len` on maps, invariant nil-fails/non-bool-errors semantics, NaN-equals-NaN and float-division-by-zero under the total order, cross-form numeric type checks, the two-`/`-per-line regex-lexing note, the timestamp string-order caveat). The executable contract behind the prose is promoted to a tracked corpus (`instance/testdata/contract/`) whose driving tests pin every documented behavior and every error probe's exact diagnostic.
